# v0.9：连续对话、操作审批与全局规则

管理员不再选择“执行 / 先看方案 / 讨论”。同一个助手会话可以先讨论，随后说“按刚才的方案修改”，完成后继续讨论。模型根据当前需求决定查询、回答或提交具体操作请求；服务端决定该操作能否执行。

## 使用方式

1. 打开助手，创建或继续会话，直接描述需求。纯讨论和查询不会要求审批。
2. 需要修改时，模型提交真实工具调用。界面显示影响范围、操作摘要和参数；此时尚未执行该操作。
3. 选择“批准此操作”，助手从这个调用继续；也可以填写理由后拒绝，助手收到拒绝结果并继续讨论。
4. 等待审批时，可以直接发送新的要求。旧的待执行调用会作废，助手根据补充要求重新处理，已完成的步骤保留。
5. 信任当前任务时，可以在会话中开启“自动同意操作”。它只作用于该会话，其他会话默认仍需审批。已经等待审批的请求仍需单独处理，不会因打开开关而自动执行。

例如：先说“讨论一下怎样让玩家私聊时无需前缀”，再说“把所有游戏的私聊触发方式统一为直接对话”。模型读取现状后请求修改平台规则；批准后继续执行，不需要切换模式或复制方案到另一处。

默认审批粒度是一次有副作用的工具调用，一次 `execute_commands` 可包含事务批次。多步插件创建、安装、运行可能产生多次审批；可按任务信任程度选择会话级自动同意。自动同意仍执行输入校验、权限、版本和完成回执检查，不等于跳过服务端约束。

## Agent 可以修改哪些全局规则

“平台规则”页面和 Agent 的 `platform_rules_read / platform_rules_update` 共用版本化配置：

| 字段 | 用途 |
| --- | --- |
| `command_prefix` | 自定义前缀，支持中文、`!` 等非空白字符串，不限制为 `/mw` |
| `prefix_requires_space` | 是否要求前缀后有一个空格 |
| `private_trigger` | 私聊需要前缀、直接接收文字或关闭 |
| `group_trigger` | 群聊需要前缀、仅被 @ 时接收、直接接收文字或关闭 |
| `group_input` | 群聊采用结构化指令或自然语言玩家 Agent |
| `agent_instructions` | 所有游戏的管理员助手工作说明 |
| `player_instructions` | 所有游戏的玩家助手公开说明 |

平台值是默认值，游戏可单独覆盖消息触发字段。修改时可选：

- `defaults`：只改默认值，保留已有游戏的单独设置。
- `all_games`：统一所有游戏，仅清除本次实际改动字段的游戏覆盖，保留其他权限和设置。

未修改的字段不提交、不重置。新游戏继承平台默认值。游戏自身的规则、交互、流程和插件仍使用原有通用命令及代码工具修改，并纳入同一审批流程。

这不是任意宿主配置编辑器：当前全局工具开放的是上表字段，数据库地址、登录密钥和操作系统权限不通过这些字段修改。新增业务模块仍可由 Agent 编写并安装代码插件；本轮没有实现任意前端组件安装或无需开发即可扩展所有平台内部 API。

## 无指令消息与公开群聊

私聊无需指令需设 `private_trigger=all`，并在游戏中启用 `player_agent_enabled`。仍只接收已绑定到该游戏的私聊，游戏权限和参与规则继续生效。切换触发方式不会自动创建玩法或开放所有交互。

群聊自然语言需设 `group_input=agent`，选择 `mention` 或 `all` 等触发方式，并启用游戏的玩家 Agent。允许在群里执行的交互还必须由管理员明确设置 `group_enabled=true` 和 `player_enabled=true`。

群聊玩家上下文只提供公开记录，不读取私聊历史、私有记录或私有裁决；私聊和群聊的模型历史分开。群聊不输出私聊记录列表。对于管理员主动开放到群聊的代码扩展，管理员仍需确保其输出适合公开；服务端不会自动理解并消除任意插件输出中的秘密。

## 服务端执行约束

- 查询和说明允许直接进行。写入、插件源码保存、依赖安装、插件执行及连续试玩默认先生成持久审批记录。
- 审批绑定具体工具、完整参数和请求时的平台/游戏状态；批准后状态变化会返回 `APPROVAL_STALE`，模型需要重查并重新提交。
- 一个模型响应有多个工具调用时，按原顺序处理。批准当前调用不会隐式批准后续调用，也不重演前面的成功步骤。
- 拒绝、补充要求或取消会保留审计结果；旧请求不能重复批准。结果不明的代码执行不能直接重演。
- 等待审批不占运行任务槽，重启后仍可处理；运行中遇到重启的任务遵循原有中断与未知结果规则。
- 自动同意只由管理员的会话设置控制。模型工具参数、全局提示或玩家消息不能自行打开它。
- 工具名称及参数需符合本轮公布的真实协议。完成声明仍可通过 `finish_task` 绑定实际调用回执进行检查，模型自定检查项不等于证明管理员的全部意图都已满足。

审批不是操作系统沙箱。获准运行的插件仍可使用宿主代码能力；连续试玩回滚的是数据库事务，不能撤销代码已经产生的外部副作用。失败也不会自动撤销此前已成功的工具步骤。

## 接口与兼容

- `GET /api/platform/rules`：读取全局规则、版本和适用说明。
- `PUT /api/platform/rules`：管理员直接保存 `{version, changes, apply_scope}`。
- `POST /api/games/{game}/agent/tasks/{run}/approvals/{execution}`：提交 `{decision: "approve" | "reject", reason}`，在同一任务继续。
- 会话创建/修改支持 `approval_mode: "manual" | "auto"`，默认 `manual`。
- 待审批任务的 `resume` 接收补充要求并作废原待执行调用；`cancel` 可取消等待中的任务。

以上接口沿用管理端认证和游戏范围校验。旧计划/只读讨论 API 保留兼容，但新助手页面统一走连续任务接口。数据库升级到 schema 11，旧会话补为手动审批，不自动开启执行权限。

## 本轮验证

2026-10-29，使用已配置的真实 `deepseek-flash`，在隔离数据库 schema 和无 OneBot 发送器的环境完成以下 9 项检查：

1. 只讨论时没有修改。
2. 同一会话能接续方案并提交操作请求。
3. 批准前保持原状态。
4. 批准后只应用所请求的全局字段。
5. 无需切换模式即可继续执行。
6. 执行后可以回到讨论。
7. 自动同意修改前缀时保留其他规则。
8. 自动同意会话确实执行了修改。
9. 已绑定私聊的无前缀消息进入 Agent 接收队列。

本机证据保存在 `.runtime/unified-live-report.json`，含模型回答和工具回执，不随更新包分发。该测试没有向真实 QQ 发消息，也没有把验收环境的规则应用到日常游戏。

回归覆盖审批前无副作用、拒绝反馈、补充要求作废、多调用顺序、参数篡改、状态过期、跨游戏认证、重复批准、重启等待保留、旧库升级、默认继承与群聊信息隔离。真实 QQ 消息投递尚未验收；当前工具环境禁止浏览器控制，因此本轮网页构建已验证，实际视觉与点击体验尚未验证。
