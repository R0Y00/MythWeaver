# v0.3 流程、对象引用与管理执行

## 使用入口

管理台的“流程与决定”提供流程定义、发起、运行历史和人工决定。新建空白游戏不附带流程；“模板库”的两个可选示例可以创建独立空间，均不绑定 QQ 群。

常用步骤配置有图形表单；高级定义使用 JSON。流程是可选、有限的执行安排，不要求存在剧情、战斗或回合。

## 管理员可表达什么

- 自动修改当前游戏的自定义记录。
- 根据输入、已确认回答或对象字段走不同分支。
- 等待管理员填写自定义字段，例如去向、公开内容、额度或其他安排。
- 决定后继续自动执行，遇到下一人工节点再次等待。
- 限定等待涉及的记录；其他记录和游戏继续使用。
- 随时取消后续步骤；修改定义或覆盖依赖数据，使旧等待失效。

流程等待前已经提交的步骤不会因为之后取消而撤销。启动、每次人工决定及后续自动步骤各自构成一次原子事务；同一事务任何步骤失败，整次回滚。跨越人工等待的步骤不属于同一事务。需要回到更早状态时使用检查点。

填写人工答案和决定说明后，可以先“预览后续影响”。平台在回滚事务里试执行，显示字段前后变化及下一次等待/结束状态，不修改真实数据。使用预演后确认会核对游戏状态指纹；期间有其他状态变化时拒绝旧预演，需重新预览。修改答案或说明会清除旧预演。

## 定义格式

游戏定义可增加 `workflows`，每个流程有显示名称、启用状态、输入 schema、起点和步骤表。

```json
{
  "label": "由管理员指定安排",
  "enabled": true,
  "schema": {
    "type": "object",
    "properties": {
      "target": {"type": "string", "x-reference": {"type_key": "note"}}
    },
    "required": ["target"]
  },
  "start": "review",
  "steps": {
    "review": {
      "kind": "manual",
      "label": "指定实际发生的内容",
      "schema": {
        "type": "object",
        "properties": {"text": {"type": "string", "minLength": 1}},
        "required": ["text"]
      },
      "locks": ["input.target"],
      "effects": [{
        "type_key": "note", "id_from": "input.target", "field": "content",
        "operation": "set", "value_from": "answers.review.text"
      }],
      "next": "finish"
    },
    "finish": {"kind": "end", "result": "已保存管理员安排。"}
  }
}
```

示例中的 `note` 必须由管理员先定义，其结构需要允许 `content` 字段。完整可运行定义见 `examples/`，没有内置 note 类型的假设。

| 步骤 | 配置 | 行为 |
| --- | --- | --- |
| effects | effects、next | 执行字段赋值、数值增加或列表追加 |
| manual | schema、locks、effects、next | 等待管理员填写 schema 字段，确认后执行本步骤 effects |
| branch | condition、yes、no | 根据确定性条件选择后续步骤 |
| end | result | 保存管理员可见结果，结束实例 |

初始输入通过 `input.字段` 读取，人工答案通过 `answers.步骤标识.字段` 读取。路径仅读取字典字段，不执行表达式或代码；赋值目标仍是记录的顶层字段。旧版交互的数据规则保留直接字段标识，兼容现有配置。

每个流程最多 40 步，每个游戏最多 30 个流程，每个步骤最多 10 项变更。发布时检查步骤引用和所有分支，禁止循环；需要重复时明确发起新实例。目前不支持定时、任意事件监听、条件自动唤醒、通用脚本或阶段生效。

## 条件

简单比较可用图形表单，组合条件通过高级 JSON 设置。

```json
{"left":{"path":"input.requested"},"op":"lte","right":{"value":10}}
```

读取对象字段：

```json
{
  "left":{"entity":{"id_from":"input.target","type_key":"proposal","field":"state"}},
  "op":"eq",
  "right":{"value":"草稿"}
}
```

支持 eq、ne、gt、gte、lt、lte、in、contains；exists 只有 left 和 op。支持 `{ "all": [...] }`、`any`、`not` 组合，最多 6 层，每组最多 10 项。数值比较不接受布尔或无限数值。缺字段返回明确错误，不由 AI 猜测。

交互也可单独增加 `condition` 作为前置条件，路径直接引用交互输入，如 `target`，不用 `input.`。人工交互会记录条件读取对象的版本，批准时再次检查，不能沿用过时条件。

## 等待与失效

`manual.locks` 是记录完整 ID 的来源路径。仅阻止参与者通过其他规则写入这些记录，不阻止全游戏。管理员可以覆盖数据：相关等待会变为 stale、解除等待范围，之后不能继续旧实例。条件已读取的对象同样进入依赖集。

修改游戏定义、修改游戏信息或恢复检查点也会使等待失效。恢复时，检查点内旧等待保留为 stale；检查点之后的流程保留为 superseded，避免历史误显示为当前仍有效的流程。流程版本递增，旧执行请求不能复用。

流程实例、输入、确认回答、依赖版本、步骤历史和等待范围保存在 PostgreSQL。正常重启可以继续等待，不重新执行此前已提交步骤。前端显示最近 200 个实例；尚未提供完整分页界面。

QQ 交互配置 `mode: "flow"`、`workflow: "流程标识"` 后，通过已有“使用”指令发起。平台仍只回公开受理结果，不自动把流程内部资料或人工答案发到群；人工节点在 Web 处理。

## 对象引用

schema 的文本字段可配置 `x-reference: {type_key: "目标类型"}`。图形字段编辑器和流程输入支持引用类型，记录表单提供选择器；高级 schema 可在对象、列表及组合结构中声明引用。

写入、规则执行、人工回答和定义发布均检查引用所属游戏、类型和归档状态。有效记录仍引用对象时，默认阻止归档目标；可先调整引用/归档关联记录，或显式在字段定义中使用 `allow_archived: true` 保留历史引用。引用本身不授予玩家读取或编辑对象的权限。

## 管理 Agent

计划助手可先调用 `query_records`、`query_events`、`inspect_flow`，再生成原子计划。读取按当前游戏隔离，最多 4 次模型请求、6 次读取、每次至多 20 条；计划最多 8 项写操作。总规划超时 180 秒，单次模型超时/输出长度继续按任务配置。初始资料是有数量限制的预览，大量数据需使用读取工具；总上下文和读取结果也有限制。没有费用金额预算或任意检索代码。

新增 `flow.start`、`flow.resume`、`flow.cancel` 管理工具。读取工具及流程工具均由服务端校验，不接受模型提供 actor、游戏范围或任意 SQL。

“预检通过后直接执行”只授权本次管理员请求，默认关闭。关闭时生成计划，之后手动执行；开启时仍先做事务预演和版本检查，范围不明仍可返回澄清。正在规划的任务可停止，已提交操作不会被取消。终止本地 HTTP 请求不保证服务商立即停止计费。只读讨论的运行中取消尚未接入。

真实模型尚未配置，这些协议与执行行为使用模拟服务商验证；不能视为真实模型质量验收。

后续 v0.4 已增加管理员流程接管/跳转、共享设置与权限命令、定义/数据迁移和退役恢复，详见 [游戏控制说明](08-agent-game-control.md)。
