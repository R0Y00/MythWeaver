# v0.8：可管理的会话与面向游戏的执行循环

## 本轮目标

把管理员助手从单条运行记录列表改为真实会话，并解决“只读了工具，没有答复或可用结果”的问题。平台仍是管理员定制的 Agent 平台：不会预装战斗、背包、剧情节点或固定游戏阶段。

## 参考的专用 Agent

本轮查阅了以下项目的官方源码或文档，没有引入它们的运行时，也没有复制其游戏规则：

| 项目 | 查阅入口 | 在本平台采用的思路 |
| --- | --- | --- |
| Concordia | [SwitchAct](https://github.com/google-deepmind/concordia/blob/main/concordia/components/game_master/switch_act.py)、[MakeObservation](https://github.com/google-deepmind/concordia/blob/main/concordia/components/game_master/make_observation.py) | 游戏行动、实际结算和各参与者的可见反馈分开组织；角色与场景由配置决定 |
| Quilltale | [Game Master](https://github.com/Aeesh/Quilltale/blob/main/src/agents/game_master.py) | 结构化状态是事实依据；叙述与状态修改分别处理，变更必须经过服务端校验 |
| MaiBot | [消息处理器](https://github.com/Mai-with-u/MaiBot/blob/main/src/chat/heart_flow/heartflow_message_processor.py) | 按会话组织收到的消息与后续处理，不把所有聊天混成一份历史 |
| DeepSeek Harness | [架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) | 持久会话、可查看的执行回执、插件工具发现和中断后继续 |

这些是设计参考。NPC 记忆检索、自动世界演化和主动私聊调度并未因此自动实现，不能据此宣称已经达到这些项目的全部能力。

## 会话与界面

- `agent_sessions` 持久化标题、游戏归属、模式、置顶、归档、软删除及时间。
- 新建、重命名、搜索、置顶、归档、恢复和回收站均通过服务端接口处理。
- 同一会话连续追问使用该会话最近 8 条运行记录及实际工具回执摘要；不同会话不混入历史。它是有限上下文，不是无限长期记忆。
- 同一会话同时只允许一个执行中的请求。归档或删除前必须先结束运行。
- 历史数据升级时每条旧运行分别迁移为一个会话，保留原始审计，不推断不存在的历史上下文关系。
- 助手默认“执行任务”；“只讨论”和“先看方案”分开选择。方案必须明确执行后才修改游戏。
- 执行卡展示中文工具名称、成功或错误、实际修改和试玩反馈，原始参数与 JSON 保留在技术详情中。
- Markdown 正文支持列表、表格及代码块；输入框固定在会话底部，草稿按游戏和会话保存在浏览器。
- 删除会话不撤销已经提交的游戏修改、插件安装或外部副作用。

接口：

```text
GET/POST /api/games/{game_id}/agent/sessions
GET/PATCH /api/games/{game_id}/agent/sessions/{session_id}
```

列表支持 `view=active|archived|trash`、`q`、`offset` 和 `limit`。执行、规划和讨论请求新增可选 `session_id`。未传时创建独立会话，兼容旧调用方式。会话历史接口默认返回最近 100 轮，单次最多 500 轮，可用 offset 继续读取；网页当前最多展开最近 500 轮。

## 让 Agent 正确创建玩法

`inspect_runtime` 新增 `authoring_contract`，包括类型、交互、效果、条件、流程、模块的真实配置字段，以及静态 response 与动态反馈的区别。

`validate_module` 在当前定义上校验一个完整模块。它不会写入数据、安装插件或执行代码；实际提交仍会校验版本、现有记录和权限。

`simulate_actions` 在一个最终回滚的数据库事务中连续执行 1–20 个交互：

```json
{
  "actor": "qq:10001",
  "actions": [
    {"interaction": "管理员实际创建的交互", "data": {}}
  ]
}
```

`actor=qq:数字` 时校验玩家可用交互和输入引用，并返回该玩家可见观察；`admin` 仅用于管理员探测，不能作为玩家授权已通过的证据。结果包含每步成功或拒绝、实际反馈、最终记录及待发消息草稿。错误步骤使用保存点回滚，之后可继续检查其他步骤。所有试运行数据、事项、审计和待发消息最终回滚，不进入 OneBot 发送队列。

可信插件进程仍然真实执行，其文件、网络等外部副作用不在数据库回滚范围内。模拟工具不会创建 OS 沙箱。

## 行动结果反馈

服务端扩展可返回可选 `feedback`：

```json
{
  "updates": [],
  "messages": [],
  "feedback": "本次行动的实际结果"
}
```

`feedback` 必须为 1–8000 字符的字符串，保存为本次自动交互的 `Submission.result`，由玩家 Agent 的真实行动回执直接返回给发起者，无需额外 QQ 绑定或 messages 授权。其他受众的通知仍用 messages，并继续校验受众、授权和绑定。

反馈由管理员信任的插件明确生成，不自动脱敏。不要把包含秘密的输入记录整段返回。manual 交互以管理员填写的裁决文字为准；流程步骤仍以流程结束结果和受众消息为准，不把步骤反馈自动提升为流程最终结果。

## 玩家 Agent 的格式修正

玩家工具包含各个开放交互的具体输入 schema。收到模型输出后先进行无副作用预检：

1. 检查游戏与授权是否仍为模型开始时的状态。
2. 检查工具名称、参数、玩家授权、可见引用及交互输入 schema。
3. 仅在格式或 schema 错误时向模型返回校验反馈，最多两次修正，整个请求限制 90 秒。
4. 通过后再次在最终事务中验证，并只提交一次行动。

权限拒绝、状态过期、资源不足以及插件运行错误不会自动重试，避免重复外部副作用。空管理规划和空讨论答复不再记录为成功回复。

## 验收与边界

`tests/test_sessions.py` 覆盖会话管理、隔离、旧表升级及模块预检；玩家、扩展和插件测试覆盖格式修正、无重复执行、动态反馈及试玩回滚。

`scripts/validate_guess_agent.py` 使用已配置的真实模型，在独立数据库 schema 中创建并测试猜数字玩法。`--resume` 继续该测试，`--verify` 用真实玩家模型验证，`--fresh` 使用单独的新建验收报告。它不启动 OneBot 发送器，不绑定真实 QQ。生成的玩法仅存在于隔离测试空间，不会自动复制到实际游戏。

不能把模型自己的“通过”声明当成最终证据：还需要检查工具回执、记录状态和真实玩家操作结果。浏览器自动化在本机设置中被关闭，因此本轮不能宣称已完成网页截图或实际点击验收。

## 更新

前端已构建的发布包不要求另一台机器重新安装 Node 依赖。停止旧平台后覆盖程序与前端构建，保留 `.env`、数据库目录和插件环境，再运行 `start-platform.bat`。首次启动自动执行 schema 10 迁移。仍采用服务器控制台运行：关闭控制台会结束平台。
