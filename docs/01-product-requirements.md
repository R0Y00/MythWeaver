# MythWeaver 产品需求文档

版本：v0.7 · 日期：2026-10-29 · 状态：设计基线，部分已实现；当前验收状态见 [首版验收跟踪](07-acceptance-status.md)。

## 1. 产品定位

MythWeaver 是由管理员定义玩法的 AI 辅助多人互动游戏平台，通过 QQ 参与，通过 Web 与管理 Agent 创建、管理和修改游戏。

平台不预设游戏一定有战斗、角色属性、背包、技能、骰子、任务、剧情主线或固定阶段。是否需要这些概念、它们叫什么、如何工作，由管理员决定。本文中的玩法示例不是平台必备功能清单。

管理员可以从空白游戏开始，只用文字、参与者和人工决定，也可以定义自己的数据、交互和规则，由 Agent 按需求创建、组合和修改运行时模块。管理员也不必从预设的几类游戏中选择。

项目已确定非商业、自托管；QQ 使用 NapCat，通过 OneBot 11 反向 WebSocket 直接接入平台，不使用 NoneBot2 等中间机器人框架。约六名玩家仅作为初期容量测试样本，不约束游戏人数或玩家关系。

## 2. 管理员决定游戏，而不是平台替管理员决定

管理员拥有全平台业务编辑和管理能力，GM/主持人可由管理员授权管理某个游戏实例。主持人、玩家等为初始权限模板，管理员可配置实际称谓、分工及授权。

| 管理员可决定的内容 | 说明 |
| --- | --- |
| 游戏中有哪些概念 | 可以有线索、提案、人物、地点、关系或自定义对象，也可以仅有文字记录；不强制创建角色卡 |
| 记录哪些数据 | 自定字段、类型、关系、可见范围及约束；不强制生命、等级、数量等字段 |
| 玩家如何参与 | 自由描述、选择、提交内容或其他已支持交互；不强制回合或特定行动分类 |
| 如何产生结果 | 固定安排、规则计算、人工指定、AI 辅助，或按不同事项组合；不是每次都要审批或掷骰 |
| 游戏如何发展 | 可以预先安排、临场决定、让玩家推动；可以没有剧情、主线、阶段或胜负条件 |
| AI 承担哪些工作 | 可只做查询/记录，也可辅助设计、扮演、总结或执行获授权操作；可关闭 |
| 使用哪些模块 | 由 Agent 创建新模块和功能，按需配置、组合、停用或替换模块；没有启用的功能不进入游戏操作界面和 Agent 工具集 |
| 运行中如何调整 | 修改定义、规则、权限、当前状态和后续安排，指定生效范围；可临时人工接管 |

“固定发生”指管理员当前的安排，不限制管理员后续修改。玩家普通输入不能擅自改定义；管理员明确命令可直接授权修改，常规操作不强制再经过 GM 批准。

常用定义、字段、交互、决定方式和状态修改，以及新模块和函数的创建，应通过界面或自然语言管理完成。平台不承诺一句话自动实现任何新算法；超出已支持能力时，管理员可以先手工处理，再按需要增加扩展，而不必放弃整个游戏。

全量业务管理不要求破坏数据库结构。平台仍保持身份校验、数据引用、事务与历史记录；管理员有权修改自己的游戏约束，并为受影响数据选择迁移方案。

## 3. 首版平台能力

以下是支撑任意游戏的基础能力，不是某种玩法的规定。游戏实例在技术上沿用 campaign_id 命名，但无需对外称为“团”。

### F01 游戏创建、参与者与权限（P0）

- 可以创建空白游戏，填写名称和说明后即可使用；模板可选。
- 将 QQ 群与游戏实例绑定；首版一个群同一时刻对应一个活动实例，私聊须明确上下文。
- 支持参与者、平台身份、外部 QQ 身份绑定、权限模板及对象/操作范围授权。
- 玩家身份与游戏内人物分开；游戏可以没有人物，玩家也可以控制多个已授权对象。
- QQ 群主/管理员不自动获得平台管理权；昵称、引用消息和角色扮演台词不构成授权。

### F02 管理员定义数据与内容（P0）

- 可新增自定义对象类型和字段，例如“线索”“提案”“嫌疑记录”；示例不构成内置类型限制。
- 首版支持文本、数值、布尔、枚举、列表、对象引用和结构化扩展字段，以及实例级可见性。
- 可只保存自由文本；只有需要自动查询、约束或计算时才补充相应结构。
- 支持定义和数据的创建、批量编辑、归档、复制、导入导出；字段增加、改名和兼容类型调整无需修改代码。
- 删除或不兼容变更须说明受影响数据和引用，提供迁移/保留/归档方案；不静默丢失数据。
- 业务约束由游戏定义或启用模块声明；平台不预置“库存不能为负”“必须有生命值”等通用游戏限制。

### F03 交互、规则与决定方式（P0 基础）

- 默认允许文本参与和管理员手工记录/决定，不要求先定义完整规则。
- 管理员可定义可用操作、输入字段、可见对象、允许执行者、前置条件、结果处理和回复方式。
- 自动规则使用 Agent 编写并持久保存的函数、表达式及状态操作；没有规则的行为可以保持未处理、请求补充或转人工，策略由管理员设置。
- 可按事项指定固定结果、规则结果、玩家选择、管理员决定或 AI 建议后决定；这是可组合的起步能力，不是游戏类型分类。
- 玩家选择与后果分开；管理员可以决定某项选择是否直接生效、按规则计算后果，或交人工决定。
- 管理员可以预拟后续发展，也可以只写“结果由我指定”；未确定内容不由 AI 擅自变成事实。
- 如需等待决定，明确只阻塞哪些对象/操作，不默认暂停整个游戏。已有提交与后续未决定部分分别记录。
- 可以增加、修改、删除这些定义，或完全不用自动规则、阶段和事件编排。

### F04 可选的建议与人工决定（P0）

- 管理员决定哪些事项需要建议、审批或人工指定；平台不要求所有玩家行为都进入审批。
- 待决定事项可包含上下文、候选结果、待填字段、相关对象和当前定义/状态版本，不强制有消耗、骰点或成功/失败两种结果。
- 有权限者可批准、修改、拒绝、指定新结果或取消；缺少最终结果时不能把建议当成已执行。
- 过期、定义变化或相关状态变化时重新检查；同一决定不能重复生效。
- QQ 提供文字交互，Web 提供完整编辑和差异查看；不假定渠道一定支持按钮。

### F05 管理界面与管理 Agent（P0 基础，后续增强）

- 界面围绕当前游戏定义生成列表、详情、编辑表单和可用操作，不固定展示角色/背包/战斗导航。
- 管理员通过表单或自然语言定义/修改对象、字段、操作、决定方式、权限及实例数据。
- Agent 先查询当前游戏定义、权限和状态，再选择工具；不能因熟悉某类游戏就自行添加战斗、奖励、人物属性或剧情结构。
- 对明确的管理员命令直接执行获授权修改并报告结果；范围不清时澄清或先给出可编辑方案。
- 复杂批量变更显示对象范围、定义差异和数据影响；支持管理员明确要求立即执行。
- 模型关闭后，手工管理、查询、记录和已有确定性操作继续可用。

### F06 状态、历史与恢复（P0）

- 平台保存当前真实状态和已提交事件；每次修改记录实际操作者、前后差异、相关定义版本及原因。
- 历史记录不依赖存在剧情、战斗或回合；也可只是玩家提交与管理员修改记录。
- AI 回顾可选，按可见范围生成，区分事实、建议和未定事项；摘要不覆盖真实状态。
- 支持检查点、无依赖操作的撤销、有依赖时的补偿或恢复分支；不覆盖后续合法修改。
- 已发送 QQ 消息无法保证撤回，恢复后需要更正通知。

### F07 游戏定义与可选模块（P0 基础，后续按需增加）

- 模块是管理员选用的能力包，不是所有游戏默认安装、创建或启用的业务流程。
- 游戏定义保存对象/字段、操作、规则、可见性、模块配置和可选的推进安排；可复制为模板，模板也可为空白。
- 模块声明新增的数据、操作、界面、Agent 工具、权限、依赖和版本；启用前给出变化说明。
- 停用后不再提供相应操作和工具；默认保留可恢复的数据。存在依赖时说明影响，不自动停用其他玩法或删除记录。
- 下面只举例说明管理员可能提出的需求，不是平台的必备模块或待开发清单。Agent 应能创建这些类别之外的新模块；新的底层能力通过扩展运行层增加。

| 可选能力示例 | 仅在管理员选择后才有意义 |
| --- | --- |
| 线索与秘密 | 谁能看到什么、发现或揭露如何决定 |
| 角色与属性 | 是否需要人物、字段有哪些、如何变化 |
| 物品与资源 | 是否存在持有/交易/数量，以及对应约束 |
| 骰子与检定 | 是否使用随机，使用什么判定方式 |
| 战斗 | 是否存在对抗、如何行动、何时结束 |
| 剧情与 NPC | 是否有叙事/扮演、哪些事实允许 AI 生成 |
| 投票或其他交互 | 参与资格、方式、结果处理由游戏定义 |
| 模拟分析 | 只有规则可执行且管理员需要时才实现对应分析 |

以上列表不封闭、不构成开发承诺；不能为了方便实现，把所有游戏都映射成战斗系统。

### F08 平台设置与扩展（P0 基础）

- 管理 QQ 连接、模型、工具授权、预算、任务、备份、数据保留及健康状态。
- 密钥可替换/撤销，不在日志和界面中回显；公开回复不能泄露私有内容。
- 平台提供停止 AI 任务和管理员接管入口；取消不撤销已经提交的操作。
- 自定义执行扩展按版本和权限安装；首版未提供隔离运行器时只安装部署端可信扩展，不执行群消息里的任意代码。

## 4. 易用性与运行中修改

管理员不应被迫先设计复杂流程图、填满一套角色/技能模板，才能开始游戏。界面默认展示当前游戏需要的概念，定义编辑和运行管理可在同一工作台完成。

修改可选择立即生效或作用于后续操作；如果游戏使用阶段，也可选择下阶段生效。定义切换使相关旧预览、未执行任务和待决定事项重新校验。已经发生的事情不因改定义自动重新发生；需要修订历史时显式执行修订或恢复。

管理员可随时改为手工处理。某个机制暂时不能自动化，不妨碍其他已经配置的能力继续使用。

## 5. 验收要求

以下是首版基础验收，不要求任何战斗或物品模块存在。

| 编号 | 验收场景 |
| --- | --- |
| A01 | 从空白游戏开始，不创建角色卡/背包/战斗/骰子/阶段，也能通过 QQ 参与、人工决定和记录 |
| A02 | 管理员通过界面或 Agent 新增自定义类型、字段、操作和决定策略，常用修改无需改代码 |
| A03 | 同一实例同时存在固定、规则处理和人工决定事项，分别按设置执行 |
| A04 | 运行中新增/修改/停用定义时，相关任务及待决定事项重新校验，历史不自动重演 |
| A05 | 未启用模块不出现在该游戏界面、命令和 Agent 工具中，模型不虚构对应机制 |
| A06 | 同一消息重复投递 10 次，同一操作仅提交一次；相同文本的新消息仍能合法受理 |
| A07 | 两个操作者并发修改同一对象时，无静默覆盖；同一人工决定只生效一次 |
| A08 | 批量修改任一目标不满足条件时整批不变；超过原子批次范围时明确说明 |
| A09 | 玩家不能改未获授权的定义/状态；模型、引用消息和跨实例 ID 不能提升权限 |
| A10 | 私有信息不出现在无权用户的查询、模型上下文、错误、摘要和公开回复中 |
| A11 | 关闭模型后仍可查询、手工主持、编辑及执行已有确定性操作 |
| A12 | 重启、换模型或 QQ 离线后，已提交状态、事件及定义版本完整 |
| A13 | 待管理员指定的内容不由 AI 补成事实；等待只影响已设定的范围 |
| A14 | 撤销不覆盖后续修改；检查点恢复与数据库/文件备份在独立环境验证一致 |
| A15 | 两套玩法不同的示例配置使用同一核心和工具，无需增加核心业务分支；其中至少一套完全无战斗、背包和随机 |
| A16 | 模块停用与定义删除检查引用/任务依赖，不丢失数据，不再执行旧操作 |

性能目标尚未测量：以六名参与者并发为初期样本，同区域普通查询/确定性操作 P95 ≤ 1 秒（不含 QQ 网络）；AI 请求尽快给出受理回执，超时不损坏状态。特定模块有额外验收时，只在选用该模块后适用。

## 6. 实施范围

| 阶段 | 交付与退出条件 |
| --- | --- |
| M0 接入与定义样本 | 验证 NapCat 直连；整理管理员选定的两套不同玩法样例，不先铺开实现所有模块 |
| M1 通用基础 | 身份、游戏定义、自定义对象、状态/事件、权限、幂等命令和手工决定；空白游戏可运行 |
| M2 首版闭环 | 定义驱动的 Web 与 Agent、基础自动规则/交互、恢复及 QQ 交互；A01–A16 通过 |
| M3 按需扩展 | 根据实际使用增加模块、交互、自动化与分析能力，不设必做的战斗/剧情模块清单 |

首版不建设通用重型工作流平台，不承诺自动实现任意玩法算法。自动化覆盖范围与游戏自由度分开：平台暂时不会自动计算的机制仍可由管理员主持并记录。

## 7. 待实际使用确定的内容

- 具体玩法、概念、模块与自动化优先级由管理员决定，不能从最初跑团例子直接推定。
- 模型提供方、预算、部署环境、历史资料导入范围待接入验证时确定。
- SnowLuma 保留为后续接入候选；当前仍为 NapCat 直连，不改变已确定链路。


## Agent 主导的操作入口（v0.5 补充）

管理员通过自然语言定义 Agent 的管理和游戏参与职责，配置结果应持久保存为可校验的规则、权限与流程。玩家 Agent 在当前身份下读取数据、理解行动并执行开放交互；GM 可随时修改定义或接管裁决。管理台承担查看、试运行、接管与恢复。具体实现与未交付边界以 [玩家 Agent](09-player-agent.md) 为准。


## 动态创建能力（v0.6）

Agent 除了配置已有功能，还能创建新模块、新数据概念、新操作与自定义计算函数。平台不维护必须逐一实现的玩法清单。运行时声明式模块已实现；任意宿主代码插件、外部集成和自定义前端扩展仍未实现。验收与实际边界见 [运行时模块](10-runtime-modules.md)。


## Agent执行与真实代码扩展（v0.7）

已增加持久执行循环、源码插件版本、真实pip/npm安装、测试和动态工具注册。参考DSH的扩展结构，继续保留本平台的状态、权限和事务服务。支持可信Python/Node代码；独立进程与依赖环境不是OS安全沙箱。范围见 [Agent harness与代码插件](11-agent-harness-and-code-plugins.md)。
