# v0.9.2：玩家聊天上下文与真实聊天验收

## 本次问题

用户报告：群聊中开局成功、第一次猜数正常，下一次只有数字的消息却被回复“没有可见的进行中对局”。此前管理 Agent 先开启群权限、再合并交互，结构化试玩均成功，但真实聊天仍失败。

代码检查发现两个关键缺口：

1. 群聊上下文按权限不提供私有状态；玩家历史又只提供请求文本，没有此前成功的公开执行回执。模型看到 `records=[]` 时，把“无权读取记录”误解为“服务端没有对局”。
2. `simulate_actions` 直接提交 JSON 行动，不经过玩家模型，而且此前只能按默认私聊受众验证。它无法证明自然语言行动选择、连续聊天记忆和群权限组合正确。管理提示词及“已验收”标识没有明确区分这些层次。

解决方式保留隐藏状态隔离，不把答案或完整私有记录交给玩家模型，也没有为猜数字增加专用路由。

## 玩家 Agent

- 明确 `records` 只是允许读取的数据，空列表不能用来断言未开局、行动失败或服务端无状态。
- 已开放交互能在服务端读取隐藏状态。玩家意图明确且输入 schema 参数完整、不需要不可见记录 ID 时，提交行动让服务端判断，不自行添加“必须先看到对局”的前置条件。
- 群聊按游戏、玩家、受众和聊天 ID 隔离，提供同一聊天最近的请求及已经公开的执行回执。不会回放其他群或私聊结果。
- 群聊旧回执仅在定义、游戏设置和平台规则的版本一致时回放，避免权限修改后重新提供旧结果；回执不是实时状态或新授权，最终仍以服务端结算为准。
- 私聊历史仍仅作为请求线索，不重新提供旧答案或旧记录，保持原有访问变更隔离。
- 结算直接使用真实反馈，去掉每次重复的“行动已受理，已按配置完成处理”。没有执行时仍明确标记未执行。

当前记忆窗口有限，不代表无限期保留整段聊天。即使历史不在窗口内，也不能根据可见记录缺失自行断言隐藏状态不存在。该提示不能保证模型在所有输入下永远正确；最终授权和状态校验仍在服务端。

## 管理 Agent 的配置要求

管理提示词和可发现的 authoring contract 增加以下要求：

- 分别检查消息触发、模型意图解析、受众上下文和服务端结算；不能只凭权限位或交互数量推断根因。
- `player_description` 应说明使用场景、参数提取和简略跟进；schema 应避免有歧义或无意义的参数组合。
- 有清晰语义的多个交互可以保留，不把所有玩法强制合并成单入口。
- 隐藏状态由服务端处理，不能用公开秘密来修补上下文。
- 修复聊天必须用原话经过真实玩家模型，至少连续三轮并检查实际行动；需要时覆盖重开、越界、结束。
- 报告区分配置检查、插件测试、结构化行动、真实模型聊天和真实 QQ 收发，不预测特定随机结果，不主动披露隐藏答案。

## 验收工具

`simulate_actions` 新增 `audience: private | group`，默认 private，回执明确 `test_layer=structured_actions_only`。它继续测试结算与玩家权限，不代表聊天通过。

新增 `simulate_conversation`：

```json
{
  "actor": "qq:已授权的测试身份",
  "audience": "group",
  "messages": [
    {"message": "重新开一把100到200", "expect_interaction": "play"},
    {"message": "150", "expect_interaction": "play"},
    {"message": "125", "expect_interaction": "play"}
  ]
}
```

示例中的 `play` 是该实例的交互名，并非平台内置玩法。工具每次最多八条消息，实际调用玩家模型、聊天历史、受众权限和交互结算，返回逐轮实际行动、答复及预期检查。没有行动或选择错误会使对应检查失败。

整个测试在独立连接的外层数据库事务中运行，结束或失败均回滚。不启用 QQ 发送器；会调用真实模型并产生模型费用。测试期间锁定目标游戏，避免与日常行动并发；应选择适当时机。代码插件仍真实执行，文件和网络等外部副作用不随数据库回滚。该工具默认需要审批，会话自动同意时直接运行。

管理端“玩家试运行”增加群聊/私聊选择；它仍会写入当前游戏，并非回滚测试，页面保留此说明。

## 完成声明的服务端检查

`finish_task` 增加 `verification_scope`：

- `receipts`：默认，只核对所列实际工具回执。
- `player_conversation`：必须引用本任务真实 `simulate_conversation` 成功回执，至少三轮、每轮含预期检查且全部通过；跨空间调用同样支持。结构化试玩、只有一轮、没有检查、失败聊天和伪装返回相同字段的代码插件都不能作为此范围的证据。

界面完成徽标改为“回执已核对”，显示核验范围。普通回执检查不会自动升级成完整聊天验收；真实聊天也不代表 NapCat 传输已经实测。

## 本轮实际证据

复制用户当前猜数字游戏的定义、权限、记录与启用插件到隔离 schema，复用已有插件环境和 DeepSeek 模型，没有修改日常对局或发 QQ：

- 群聊七轮：重开 100–200 → 150 → 125 → 越界 → 重开 → 150 → 125，每轮实际选择 `play`，反馈正常。
- 私聊三轮：重开 → 150 → 125，每轮实际选择 `play`。
- 不提供新聊天历史、直接说 125，仍实际提交猜测，由服务端读取已有对局。
- 模拟 OneBot 群聊入站→玩家模型→结算→出站队列，三轮回执保持在同一群，未启动真实发送。
- 群聊模型可见记录始终为空，隐藏记录没有暴露；数据库最终与测试前一致。
- 管理 Agent 实际读取配置、调用 `simulate_conversation`，使用 `player_conversation` 范围完成回执核验，没有修改副本配置。

完整回归 264 项通过，随后补充的 OneBot 连续链路与伪造聊天证据拒绝测试也通过。

本机详细证据为 `.runtime/player-conversation-live-report.json` 和 `.runtime/manager-chat-acceptance-live-report.json`，不随公开更新包分发。真实 QQ 上线后的连续对话仍需实际使用观察；本轮不把隔离模型测试称为真实 QQ 验收。
