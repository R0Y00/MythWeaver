# v0.9.7：Agent 易用性与行为约束审查

审查日期：2026-10-30。

## 结论

平台已经有灵活的数据、模块、插件、权限和管理审批能力，但尚不能把“GM 给一份工作说明”稳定地变成“完整实现并验证的专用玩家助手”。这次反馈成立：问题同时存在于程序输出、上下文、管理助手的交付方式、业务流程和测试标准。增加一段“不要乱说”的提示词不能替代这些工作。

本次先修复已定位的问题，并建立更有用的行为测试条件。**不宣称某个已有游戏的全部道具、商店、确认流程和特殊裁决都已经实现。** 另一台电脑上的具体游戏配置未在本次直接读取；聊天转录能揭示问题，不能证明所有规则的实现情况。

## 参考的设计方法

1. [Rasa CALM：业务逻辑、对话理解和对话修复](https://learning.rasa.com/rasa-pro/introduction-to-calm/)。模型理解表达和补充参数，流程规定需要哪些信息、何时转移状态；闲聊、追问和中断也属于正式设计。本平台应让管理 Agent 按 GM 的规则生成流程，而不是让 GM 学流程配置，也不是内置一种固定游戏。
2. [Pydantic AI：Deferred Tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/)。需要人决定的工作应保存待办、等待、恢复；审批不能代替工具内部的授权校验。这里保留现有管理审批，并补充玩家向 GM 交接问题的实际入口，没有更换框架或依赖。
3. [Anthropic：Writing effective tools for agents](https://www.anthropic.com/research/writing-tools-for-agents)。工具需要清楚的职责、与任务相关的反馈以及真实任务评测，不能把面向程序员的原始字段直接当作用户界面。这次把玩家回复和管理调试数据分开，扩展资源与不执行行为的断言。

这是对设计方法的借鉴，没有照搬第三方代码，也没有将平台改成固定技能清单。

## 已定位的问题与改动

| 问题 | 根因与证据 | 本次处理 |

| 行动后出现完整 JSON、数据库 ID、长背包 | `player.private_reply` 在每次有 action 时无条件序列化 records；不是模型自行输出 | 删除强制追加；数据仍保存在管理回执中，玩家只收到答复 |

| 私聊追问后，“确认/不用了/选第二项”缺上下文 | 私聊历史只回放玩家请求，不回放助手刚才问的问题 | 同一玩家、受众、会话内，规则版本和整个状态戳均一致时允许回放私聊回复与回执；状态或权限变了则不回放 |
| GM 工作说明没有稳定进入管理上下文 | Harness 初始只带空间名称和版本，游戏 instructions 需模型自己另查；还继承旧方案 Agent 的提示再逐段替换 | 管理提示独立，不继承旧方案模式；每轮刷新平台和当前游戏的管理员说明 |
| 管理端让 GM 决定 schema、权限位、数据层方案 | 缺少面向非技术 GM 的工作流程 | 明确让管理 Agent 自行选择实现，只问确实缺失的业务规则；区分“已实现并测过 / 仅说明 / 待资料 / 不在本次范围” |
| “必须确认”只写进说明，容易跳过 | 自然语言不是服务端状态机 | 管理提示及可发现 authoring_contract 明确要求持久待确认阶段、确认/拒绝入口、资源和版本重检；本次**未增加通用玩家交易确认引擎** |
| “问作者”可能只是一句回复 | 原玩家工具只有 submit_action，未定义人工交互时缺交接入口 | 新增 request_gm，创建始终 pending 的 `_review` 待办；不执行资源修改 |
| 测试只验证能调用、回复有某个词 | 缺少“不应该执行”和精确资源断言 | 连续自然语言测试新增行动状态、状态是否变化、记录字段、禁止输出、回复长度和预期错误检查 |
| 没有预期也可能显示“通过” | 空检查集合被当成全部通过 | 无预期的测试只算观察，passed=false、asserted=false；管理界面明确显示 |
| 网页试运行像接口调试器 | 单次表单后直接展示整份 JSON | 改为连续对话，输入普通 QQ 号、可选择现有参与者、区分群聊/私聊、显示行动或待裁决状态；技术回执折叠，资料按需查看 |

## 三种约束应分别承担什么

### 提示词：角色、沟通、如何使用工具

管理助手负责把 GM 的业务要求做成可用能力，不向 GM 转嫁技术设计。玩家助手根据管理员定义参与，不拥有管理权。问候简短回应；查询只答所问；缺参数问玩家；规则争议交 GM；不替玩家选贵重消耗品或自己确认。

平台和游戏的玩家工作说明单独放入 system 消息，可见资料作为数据输入。仍由服务端验证工具、输入、目标、身份与权限；system 消息不是模型绝不犯错的保证。

### 服务端：不能依赖模型自觉的规则

金额、库存、限购、次数、条件、隐藏映射、状态转移和授权写入，应在规则或插件中执行；人工裁决前保持 pending。购买确认应保存具体待确认内容和依赖版本，再在确认后重新验证并原子扣除。**管理审批、玩家确认、GM 裁决是三种不同的决定，不能相互代替。**

管理员仍可以定义任意游戏框架、安装可信插件或修改全局规则。这些约束区分不同角色和执行阶段，不固定平台必须有哪些玩法。

### 测试：验证真实玩家行为和持久结果

服务端成功提交，并不证明理解正确。测试应检查：

- 问候、查询、缺参数、拒绝时不修改资源。
- 要求确认的规则：确认前未扣除，拒绝后未扣除，确认后正确扣除且不重复执行。
- 继续行动能接上上下文；换玩家、私聊/群聊和不同会话不会串线。
- 不足、越界、限购等拒绝保留原状态，错误原因与规则一致。
- 需要 GM 的问题确实进入待办，裁决前不结算。
- 关键字段与预期精确一致，隐藏字段及技术调试内容不进入玩家答复。

这些场景按具体玩法选择；不能要求所有游戏都有购买、体力或战斗。

## 如何使用新测试条件

`simulate_conversation` 仍使用真实 PlayerAgent 决策与结算路径，在独立事务中连续多轮执行，最后回滚，不发送 QQ。新增条件如下：

```json
{
  "message": "不用了，不买了",
  "expect_action": "none",
  "expect_state_changed": false,
  "expect_records": [
    {"id": "管理员查到的实际记录ID", "path": "/data/coins", "expected": 50}
  ],
  "expect_reply_not_contains": ["type_key", "隐藏值"],
  "expect_reply_max_chars": 300
}
```

- `expect_action`：none / applied / pending；“有行动”与“实际改了资源”分别检查。
- `expect_state_changed`：比较游戏定义、权限、插件、数据、提交、流程等状态戳，忽略测试对话本身和审计事件。提交 GM 待办会改变状态；只检查资源未变时用 expect_records。
- `expect_records`：id、JSON Pointer path、expected。可检查 `/data/...`、`/version`、`/visibility`、`/archived`；记录必须属于被测游戏。可断言隐藏服务端数据，但只向管理测试工具返回布尔检查结果，不交给玩家模型。
- `expect_reply_not_contains`、`expect_reply_max_chars`：检查最终玩家文本，不是只检查模型原始回答。
- `expect_error_code`：规则拒绝也是可以预期的结果；还应断言状态和资源不变。

管理 Agent 已能发现这些参数。无断言不算验收；错误会以失败检查保留，不能因为回复含“成功”就忽略实际扣错资源。

## 现在 GM 怎么用

1. 在管理对话中描述需要助手负责什么，粘贴完整业务说明。需要开发时直接提出“做成可用的玩家助手，列出未实现部分并测试”；不必选择 schema 或插件实现。
2. 管理助手形成具体变更，按当前会话的审批方式执行。纯讨论不应产生修改。
3. 在“游戏设置 → 和玩家助手试聊”输入玩家 QQ 号并连续发消息。这里**会修改当前游戏数据**，不会发送 QQ；清空聊天不撤销已经发生的变化。需要回滚测试时，让管理助手使用 simulate_conversation。
4. 玩家遇到需要 GM 裁决的情况，助手可以发起 request_gm。GM 在“互动工作台”处理“请GM裁决”。这类待办仅记录问题和人工决定；**不自动执行问题中描述的资源修改，也不自动发送 QQ 通知**，需要结算或通知时另行明确操作。

试聊重试同一条失败请求会保留请求编号，避免因为网络回执丢失立即重复扣除；状态已过期仍需核对当前记录再继续。技术回执保留在折叠的“排查详情”中。

## 尚未完成，不能用本次更新代替的工作

1. **逐条业务覆盖与版本管理。** 提示已要求列出覆盖情况，但尚没有强制持久化的“原文条款 → 可执行规则 → 测试”映射。管理助手仍可能漏项；应增加可见的覆盖表和未完成清单。
2. **通用玩家选择与确认。** 现有自定义模块/插件能够实现，但 GM 不应反复要求 Agent 补齐。下一步应提供可复用、可配置的收集参数、报价、等待玩家、拒绝、过期、执行阶段，并保持现有自由模块能力。
3. **完整的 GM 裁决闭环。** 本次补齐待办入口；自动将裁决投递给正确玩家、继续原流程仍应由显式规则与授权控制，尚未统一做成低门槛配置。
4. **正式数据与测试空间。** 网页试聊目前是显式的真实写入；还应提供持续的隔离试玩空间和对比/恢复入口。不能通过每次重放全部聊天来伪装连续测试，否则随机结果会漂移。
5. **按需读取和呈现。** 已取消强制倾倒记录，但模型仍会读全部授权记录；数据过大仍可能报上下文预算错误。后续需要按问题读取和由 GM 指定重点字段，不靠截断规则原文解决。
6. **整份游戏的业务验收。** 某次聊天、几个插件 tests、甚至一套真实模型用例都不等于复杂道具与所有边界已通过。现有具体游戏需要逐项检查，不能只改平台提示词就宣布修复所有玩法。

私聊回放采用保守的状态戳校验，其他被纳入快照的游戏变化也可能使旧回复不可回放；持久确认状态仍必须由规则流程维护，不能把聊天记忆当作确认凭据。可信插件的文件/网络副作用也不能由测试事务回滚。

## 本次验证

验证结果：

- 完整自动回归 **315 项通过**，包含原有权限、事务、模块、插件、管理审批和新增玩家体验检查。
- 真实 **deepseek-flash 连续 7 轮通过**：问候、询价、拒绝、再次询价、确认购买、查询余额、未知能力交 GM。使用虚构票务规则和虚构玩家，包含 25 个可见物品以检查问候不会倾倒背包；确认前余额保持 5，确认后变为 2，GM 待办始终 pending。数据最终回滚。
- 上述真实模型测试中的购买确认**仅依赖该测试玩法的提示**，用于检查模型表现，并不构成服务端无法绕过的确认机制，也不代表长期概率保证。
- 前端 TypeScript 检查与 Vite 构建通过；HTTP 请求编号及登录请求回归通过。
- 修改文件的凭据扫描无发现，Git 差异格式检查通过。

所有数据库测试使用临时实例；日常 Web、OneBot 和项目数据库保持停止。没有进行浏览器视觉验收，没有直接验收另一台电脑的具体游戏，也没有向真实 QQ 发送测试消息。

## 更新方式

从本次开始不再制作新的更新包，代码通过 [GitHub 仓库](https://github.com/R0Y00/MythWeaver) 更新。

- 已通过 Git 部署的 Windows：运行 `update-platform.bat`。现有脚本检查本地改动及分支关系，停止控制台、备份数据库、快进更新，需要时更新依赖并构建网页，然后重新进入控制台。
- 旧压缩包目录没有 `.git` 的，不能只把 update-platform.bat 复制进去就使用 Git 更新。先按 [Windows 部署文档](14-windows-deployment.md) 备份并迁移为 Git 部署，保留自己的 `.env`、数据库、插件和 NapCat 配置；不要用 git reset --hard 覆盖旧目录或把整个旧环境上传到公开仓库。
- 本次变更不需要新的数据库表结构迁移；启动仍执行平台原有的版本迁移检查。
