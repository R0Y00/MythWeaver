# v0.4 管理 Agent 的游戏控制能力

## 本轮标准

管理员在管理台可用的已实现游戏业务，Agent 应能通过同一业务服务完成；权限来自实际登录的管理员，不来自模型生成的身份文字。当前共享命令目录有 25 项，可通过“游戏控制台”查看实际参数结构与预演，也可交给“助手工作区”处理。

这表示对已实现游戏业务的完整管理入口，不表示能凭空增加尚未开发的算法、模块或平台功能。多管理员委托、模块运行器、历史分支与逐事件补偿仍未实现；真实模型尚未配置，模型理解质量尚待联调。

## 实际共享命令

| 范围 | 命令 | 行为 |
| --- | --- | --- |
| 游戏空间 | game.create、game.update、game.clone | 创建空白游戏、修改名称/说明、复制框架到独立游戏 |
| 定义与迁移 | definition、definition.migrate | 兼容修改，或连同指定记录迁移/退役后原子发布新定义 |
| 记录 | entity.create、entity.update、entity.retire、entity.restore | 创建、替换、可见标记、归档、可恢复退役，以及按当前类型/数据结构恢复 |
| 内容与结果 | submit、decide、submission.revise | 提交、正常批准/拒绝、修订参与记载及指定状态/结果 |
| 设置与权限 | policy.update、participant.update | 暂停、指令前缀、自由输入策略、白名单、游戏说明、别名、封禁/恢复 |
| 群绑定 | channel.bind、channel.unbind | 绑定/解绑当前游戏群，解绑取消相关排队任务，不抢占其他游戏的绑定 |
| 检查点 | checkpoint.create、checkpoint.restore | 保存、恢复，恢复前自动保存安全检查点 |
| 模板 | blueprint.save、blueprint.create、blueprint.instantiate | 保存当前框架、保存独立模板、从模板创建独立游戏 |
| 流程 | flow.start、flow.resume、flow.cancel、flow.redirect | 发起、填写人工决定、停止、管理员接管并跳到指定步骤 |

命令目录与类型化参数来自 `mythweaver/command_catalog.py`，Agent 不再维护另一份较弱的工具校验表。游戏内设置、参与者、群绑定、检查点与已有数据/流程 HTTP 入口调用相同命令服务；创建空白游戏和全局模板入口复用相同业务实现。

模型服务商密钥、平台登录凭据、主机操作与群消息发送不在此游戏命令集内。投递重试仍由连接诊断入口管理。参与者管理只控制参与权限，不授予平台管理员身份。

## 如何让 Agent 操作

1. 配置服务商与管理规划模型。
2. 在助手工作区说明目标、范围和所需结果。
3. 默认只生成计划；需要直接执行时，开启“本次请求：预检通过后直接执行”。
4. Agent 可用 `inspect_capabilities` 查询共享命令参数，再用 `list_controls` 查询设置、参与者、群绑定、检查点、退役记录、模板和参与事项；原有记录/事件/流程读取工具继续可用。
5. 参数、权限和当前状态经服务端校验，在回滚事务内预演；实际执行仍检查状态指纹并原子提交。

例子：

- “将游戏改名，暂停玩家新提交，把自由输入设为直接记录；其他设置保留。”
- “将便签改成提案，把 text 改成 content。按现有记录逐条迁移，先保存恢复点。”
- “不再使用旧线索类型，把这些记录退役，保留恢复副本，然后移除该类型。”
- “接管这个等待流程，跳到 finish；不要重做之前步骤。”
- “修订这条记录的文字结果，但不要重新执行之前的数据变更。”
- “恢复到指定检查点，保留恢复前状态，并停止旧排队任务。”

这些是能力示例，不是已经配置真实模型后的质量保证。目标不明确时应澄清，不能由模型自行挑选记录或改写未来发展。

## 迁移、退役与恢复

`definition.migrate` 接受完整新定义、明确的记录 changes（完整 ID、版本、目标类型、数据、可见标记、归档状态）与 retire 列表及原因。最多 100 条 changes 和 100 条 retire，仍受 HTTP 128 KB 请求上限约束；不能将大数据迁移假称为无限原子批次。

平台先保存安全检查点，再在同一事务中处理记录，最后检查全部保留记录的 schema 和引用。字段重命名、类型调整及删除旧概念由明确的转换数据实现，不自动猜测。任何失败会回滚记录、新定义、安全检查点和事件。

退役记录保存在独立恢复区，保留原数据与原因；有效记录不能留下指向已退役对象的悬空引用，允许归档引用也不能绕过此检查。恢复可指定新 type_key 与 data，使其符合当前框架。对象版本账本保留，恢复不会使旧编辑请求重新合法。

## 修订与流程接管

`submission.revise` 可以修改参与内容、交互标识、状态和文字结果；不重演已发生的规则副作用。重新设为 pending 时检查当前条件和目标依赖，后续批准仍走正常执行。与实际状态相关的修订应另行修改记录或恢复检查点。参与事项的版本账本跨检查点保存，消失后重新恢复也不复用旧版本。

`flow.redirect` 允许管理员修改初始 input、指定已定义人工步骤的 answers，并跳到当前定义中的任一步骤。它会清除旧等待依赖，按当前定义重新推进，直到下一个人工节点或结束。已有步骤结果不会撤销；显式跳回自动步骤可能再次产生相应效果，预演会显示这些变化。每次接管记录原因、前后状态与新版本。

## 预演与实际执行

界面和 Agent 的预演都产生类型化计划、操作返回值及新增审计事件中的具体前后差异。预演事务回滚，不会留下参与者、群绑定、模板、新游戏、恢复点或记录变更。新建对象的预演编号是临时编号，执行后以真实结果为准；同计划不支持引用之前步骤临时生成的 ID。

计划仍最多 8 项命令，15 分钟有效；批次 HTTP 接口最多 50 项。迁移是自身有明确边界的一个命令。游戏版本、设置版本、参与者版本、记录版本、参与事项版本、流程版本、退役记录和群绑定进入状态指纹，防止在过时预演上直接提交。

API：

- `GET /api/games/{id}/capabilities`：实际共享能力与 schema。
- `POST /api/games/{id}/commands`：`{kind,payload}`，要求管理员会话、CSRF 与 Idempotency-Key。
- `POST /api/games/{id}/commands/preview`：`{commands,explanation}`，返回未执行计划。
- `POST /api/games/{id}/agent/plans/{plan}/apply`：执行同一计划，重复请求返回已提交结果。
- `GET /api/games/{id}/retired`：最近 200 条可恢复退役记录。

原有具体业务 API 保留。游戏命令没有任意 SQL/代码入口，QQ群输入不能通过提供 actor 或工具名称提升管理权限。

- 最终数据库备份 `.runtime/backups/20261029-112319.dump` 已恢复到独立数据库，验证 3 个游戏、35 条事件、2 个流程实例，未覆盖运行库。
- 没有绑定真实 QQ 群，没有配置真实模型。自然语言理解、规划质量和真实计费尚未验收；不能据此宣称所有需求已完成。
